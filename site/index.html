The problem

Raw schema access makes the model guess at things that aren't guesses.

Two failures follow directly from "LLM → raw SQL": invented business logic, and no way to prove access control was ever actually enforced.

Business meaning is implicit

Nothing in a subscriptions table tells you what "churn" means, whether MRR includes trials, or how CSAT should be aggregated. The model invents an answer — differently, each time it's asked.

Permissions are a suggestion

"Don't show PII" in a system prompt can't be proven, audited, or enforced. If the model can see the schema, it can query anything in it — and sometimes will, regardless of instructions.

The solution

Three layers between the model and Postgres.

The model never sees raw tables. It plans against retrieved, role-scoped business context — and every generated query is independently re-checked against the real schema and permissions before it's allowed to run.

retrieved via pgvector, scoped to the caller's role enforced on the parsed SQL AST, not the prompt SELECT-only DB role as the final backstop
The benchmark

500 questions, ground truth computed before either pipeline runs.

No LLM-as-judge. Every question comes from one of 16 metric templates with known-correct SQL; the expected numeric answer is computed directly from Postgres first. "Correct" means the pipeline's number matches it.

Engineering process

The first run said the opposite. That's the part worth reading.

The initial full benchmark showed the AI Data Plane doing worse than raw SQL — the opposite of the thesis. Investigating instead of reporting it surfaced three real bugs.

01

CTE output columns flagged as hallucinated

The SQL parser has no concept of WITH scoping — WITH x AS (SELECT ... AS value) SELECT value FROM x reported value as an unresolvable column, indistinguishable from a genuine hallucination. Fixed by tracking each CTE's own output aliases.

02

SELECT * silently bypassed column permissions

A star column comes back from the parser as a literal wildcard marker that matches no real column name — so it was checked against neither the hallucination rule nor the permission rule. A column-restricted role could SELECT * and get everything. A real security gap, not a benchmark artifact.

03

Retrieval was starving the model of schema grounding

Fixing 01 and 02 barely moved the hallucination gap. Root cause: similarity search returned only the top 10 of ~26 semantic-layer entries, and a table's exact column names — which only live in its entity definition — would often get crowded out by better-matching metric entries. Always including the full entity catalog dropped hallucination from 30-57% to 2% in one fix.
